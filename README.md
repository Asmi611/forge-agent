# Forge Agent

An editor-native VS Code coding agent built on **TrueForge** (local mode).

Proposals are generated by the agent, reviewed per hunk by the developer directly in the editor, and applied to workspace files only upon explicit human approval.

- **Fork point:** Built completely **from scratch** (no upstream fork).
- **License:** [MIT License](LICENSE)
- **Submission Kit & Write-up:** See [docs/07-SUBMISSION-KIT.md](docs/07-SUBMISSION-KIT.md)

## Architecture Overview

Forge Agent couples the TrueForge agent harness with VS Code's native editing and diff review UX:

- **TrueForge Local Harness:** Runs on `localhost:8790`. Manages agent sessions, multi-turn reasoning loops, and tool orchestration.
- **Client-Driven Architecture:** The VS Code extension acts as a client to TrueForge. The engine communicates with TrueForge via its HTTP API (`/api/v1/sessions`, `/api/v1/turns`, `/api/v1/events`).
- **Editor Capabilities as MCP Tools:** The extension exposes workspace navigation and proposal tools over MCP: `repoMap`, `searchWorkspace`, `findSymbol`, `readFile`, `reportContext`, `proposeEdit`, `createFile`, and `runCommand`.
- **Approval-Gated Proposal Lifecycle:** `proposeEdit` and `createFile` are configured with `require_approval_for_tools`. TrueForge pauses execution and emits `tool.approval_required`. The engine computes unified diff hunks, displays interactive CodeLens / comment UI in VS Code, and waits for developer review. The approved decisions are posted to TrueForge (`/events`), and the **same turn stream continues** with truthful tool acknowledgments.
- **Single Point of Mutation:** Neither the engine nor MCP tools write to workspace files. Only `ApplyManager.ts` and `UndoManager.ts` modify files via VS Code's `WorkspaceEdit` API after developer review.
- **Terminal Security:** `runCommand` enforces an allowlist policy and runs argv commands without shell strings (`shell: false`). Commands require confirmation prompts.
- **RunBudget & Loop Guard:** Cumulative per-run token budget tracks prompt seed, mentions, and tool responses. The loop guard blocks repetitive duplicate calls (3 identical calls without state change) while allowing legitimate test re-runs after code edits.
- **Dual-Profile Resilience:** Seamless failover between `forge-primary` and `forge-fallback` on auth errors (400 invalid key, 401, 403) or rate limits (429) if no hunks have been applied yet.

## Starting TrueForge Locally

TrueForge runs as a local service. In a separate terminal (PowerShell on Windows):

```powershell
$env:NODE_OPTIONS="--dns-result-order=ipv4first"
npx @truefoundry/trueforge@latest
```

> **Note:** The `$env:NODE_OPTIONS="--dns-result-order=ipv4first"` environment variable avoids intermittent IPv6 localhost "Headers Timeout" errors in Node.js.

TrueForge web UI will be accessible at [http://localhost:8790](http://localhost:8790).

## Agent Setup & Model Configuration

API keys are stored exclusively inside TrueForge. **No API keys or secrets ever live in this repository or git.**

### 1. Add Model Providers in TrueForge UI

1. Open [http://localhost:8790](http://localhost:8790).
2. Navigate to **Model Providers**.
3. Add your model provider credentials (e.g., Google Gemini and Groq).

### 2. Configure Local Agent Profiles

Copy the example configuration files to their local counterparts (both are gitignored):

```bash
cp forge/models.example.json forge/models.local.json
cp forge/setup.example.json forge/setup.local.json
```

Edit `forge/models.local.json` to point to your provider model IDs.

### 3. Register Agents and MCP Connector

Run the automated setup script to configure TrueForge agents and connect the editor MCP server:

```bash
npm run forge:setup
```

This idempotently registers:
- MCP Server: `forge-editor`
- Primary Agent: `forge-primary`
- Fallback Agent: `forge-fallback`

### 4. Optimize Reasoning in TrueForge UI

1. Open [http://localhost:8790](http://localhost:8790).
2. Under **Agents**, open `forge-primary` and set reasoning effort to **Low**, then click **Update Agent**.
3. Open `forge-fallback`, set reasoning effort to **Low**, then click **Update Agent**.
4. Under **MCP Servers**, verify that `forge-editor` is listed.

## Running the Extension

Open the `forge-agent` folder in VS Code and press **F5** (or open the **Run & Debug** panel):

- **"Run Extension (mock)"**: Launches the Extension Host with `fixtures/demo-workspace` using the built-in mock engine. Ideal for fast UI testing without TrueForge running.
- **"Run Extension on Flask"** (or Flask A/B/C): Launches the Extension Host with the live TrueForge engine bound to the Flask worktree. Note that paths in `.vscode/launch.json` can be adjusted to match your local folder structure.

## Flask Demo Environment Setup

The demo tasks run against `pallets/flask` pinned to version `3.1.3` (commit `22d92470`).

### 1. Create Git Worktrees

Create three isolated worktrees outside the `forge-agent` directory:

```bash
git clone https://github.com/pallets/flask.git flask-repo
cd flask-repo
git checkout 3.1.3
git worktree add ../flask-demo/flask-A 3.1.3
git worktree add ../flask-demo/flask-B 3.1.3
git worktree add ../flask-demo/flask-C 3.1.3
```

### 2. Set Up Virtual Environments (Python 3.13)

For each worktree (`flask-A`, `flask-B`, `flask-C`), create a dedicated venv and install dependencies:

```powershell
cd ../flask-demo/flask-A
py -3.13 -m venv .venv
.\.venv\Scripts\activate
pip install -e .
pip install "pytest<9"
```

Repeat for `flask-B` and `flask-C`.

### 3. Verify Baseline

In `flask-A`:

```powershell
pytest tests/test_cli.py -q
```

Expected baseline output: **55 passed, 3 skipped**.

## Tested Models & Declared Costs

| Profile | Model | Host / Provider | Role | Approximate Cost |
|---|---|---|---|---|
| `forge-primary` | `google-gemini/gemini-3-5-flash-lite` | Google Gemini via TrueForge | Primary for Tasks A and C | $0 (Free Tier) |
| `forge-primary` (Task B) | `google-gemini/gemini-3-5-flash` | Google Gemini via TrueForge | Primary for Task B (rate-limited -> auto-failed over) | $0 (Free Tier) |
| `forge-fallback` | `groq/gpt-oss-20b` | Groq via TrueForge | Fast fallback on key/rate-limit error | $0 (Free Tier) |

- **Zero Direct Provider Calls:** All models are accessed exclusively through local TrueForge. No model SDKs are bundled in the extension.
- **Automatic Failover:** When `gemini-3-5-flash` encountered rate limits during Task B, the resilience manager automatically failed over to `gemini-3-5-flash-lite`, completing the run seamlessly without human intervention.
- **Manual Model Switching:** Update `forge/models.local.json` and run `npm run forge:setup`. Provider keys remain secure within TrueForge.

## Demonstration Tasks

1. **Task A — Inline Edit (`Ctrl+K`)**:
   - Open `src/flask/cli.py` in `flask-A`, select the `get_debug_flag` function.
   - Press `Ctrl+K`, enter the prompt to invert the default behavior.
   - Per-hunk diff renders in editor. Review and accept hunks -> click Apply.
   - Verify changes with test execution. Quick Undo / Redo restores exact state.
2. **Task B — Agent Mode (Multi-File Edit & Verification)**:
   - In `flask-B`, open the Forge Agent panel.
   - Prompt: *"Add a new built-in CLI command flask config that prints the loaded application's configuration as JSON, masking the values of any key containing SECRET, PASSWORD, TOKEN or KEY as '***'. It must appear in flask --help, be covered by a test, and be documented alongside the other built-in commands."*
   - Agent discovers and proposes modifications across `src/flask/cli.py`, `tests/test_cli.py`, and `docs/cli.rst`.
   - Review each file's hunks individually. Apply changes.
   - Agent requests to run `pytest tests/test_cli.py -q` via `runCommand` (confirmation prompt). All tests pass.
3. **Task C — Resilience & Automatic Failover**:
   - Provide an invalid API key on the primary profile in TrueForge.
   - Run the task in `flask-C`. Resilience manager detects auth failure, initiates instant failover to `forge-fallback` without retries, and displays fallback diff. Workspace remains untouched until approved.

## Known Limitations

- **(a) Context Seed Heuristics:** The initial lexical seed can miss the optimal file when prompt descriptions are highly abstract (Task B in agent mode benefits from explicit hints to inspect `cli.py`, `test_cli.py`, and `cli.rst`).
- **(b) Fallback Multi-turn Limitations:** Groq reasoning models can struggle with multi-turn tool calling; fallback is most reliable when proposing changes on the initial turn.
- **(c) Free-Tier Rate Limits:** Free-tier provider quotas (e.g., ~20 requests/day per Gemini model) require deliberate rate management.
- **(d) Model Fallibility:** Language models can generate incorrect hunks; granular per-hunk human review is essential.
- **(e) Experimental TrueForge SDK:** The engine uses TrueForge's HTTP API directly rather than the experimental SDK client.
- **(f) Terminal Allowlist Scope:** The `runCommand` terminal allowlist provides permission gating, not an operating-system sandbox.
- **(g) Token Estimation:** Token usage is estimated using standard `character_count / 4` heuristics.
- **(h) Lexical Search:** Workspace symbol and context ranking uses lexical matching rather than semantic embeddings.
- **(i) Single-Root Workspace:** The current MCP server assumes single-root workspace folders.
- **(j) Session Volatility:** Paused sessions awaiting human review are not persisted across VS Code window reloads.
- **(k) Diff Editor Keybindings:** Manually saving (`Ctrl+S`) directly inside VS Code's native diff editor can bypass `ApplyManager` validation.
